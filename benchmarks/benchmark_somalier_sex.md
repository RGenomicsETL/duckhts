Somalier X/Y sex evidence at scale
================

`duckhts_somalier_sex()` reduces a sample-by-panel count relation (one
row per sample and panel site) to one row per sample: the mean autosomal
depth over sites that pass the relatedness gate, the X and Y depth over
usable sites, and the X genotype counts. It is a single scan and hash
aggregate with one group per sample, so its live state is samples × a
few numbers plus the panel-sized join side; the count relation is
streamed.

## Inputs

No registered public cohort has X/Y sites in a Somalier panel, so this
workload is synthetic and generated by
`benchmark_somalier_sex_run.R --data`: a 20,000-site panel (17,000
autosomal on 22 contigs, 2,500 chrX, 500 chrY) and counts for 500, 1,000
and 2,000 samples (1×, 2×, 4×; 10, 20 and 40 million rows), with depths
8–57 and a mix of homozygous and heterozygous balances. Growth is along
samples only; the panel is fixed. Because the data are synthetic the
report certifies memory and scaling, not the biology; agreement with
Somalier v0.3.4 is tested separately by
`test/scripts/somalier_sex_differential.R`.

## Method

`benchmark_somalier_sex_run.R` runs each cell as fresh processes, three
repetitions interleaved across cells, at one and four threads, each with
`memory_limit = '128MB'` and an empty temporary directory. Each worker
attaches the count database read-only, times the public SQL macro
including fetching the result into R (which is consumed: every sample
must have a call and a status), and records DuckDB’s peak buffer memory
and temporary-directory size from the query profile and the process’s
peak RSS (VmHWM). The database file is read from a warm page cache.
Every row records the git revision of the tree and the SHA-256 of the
bundled extension the process loaded; the report requires one of each.

`overhead_mib` is the median peak RSS of the empty-run processes and
`budget_mib` is the ceiling declared in the report source: overhead + 3
× live state + `memory_limit`. Every cell stays within it and no cell
spills. DuckDB’s peak buffer memory, the maximum of the query profile,
is reported without a gate: it reaches about twice `memory_limit` for
the attached file-backed relation, and the first measured matrix led to
withdrawing a `buffer <= memory_limit` gate that had been declared for
it.

| threads | time_exponent |

|       1 |          0.93 |
|       4 |          0.94 |

The 1× single-thread median is 1.98 s, under the 5 s floor of
`STYLE.md`, so this report gives no timing verdict at that scale; time
is shown at 2× and 4× and the fitted exponent above (expected linear
work, limit 1.25) is a scaling check, not a claim about a production
cohort. Memory does not depend on that floor.

## Limits

- Synthetic counts, no registered public X/Y cohort.
- Panel size is fixed at 20,000 sites; only samples grow.
- The buffer-pool allowance in the ceiling covers evictable pages of the
  scanned count relation; it makes the ceiling loose relative to the
  live state. What the gate certifies is that the process stays within
  overhead + live state + that bound with no spill, not that the live
  state alone is that small.
