# DuckVEP / bcftools csq port plan (2026-06-09)

Status: open design and implementation backlog. This is planning guidance for a DuckDB-native VEP/csq layer; it is not yet a compatibility claim.

## Purpose

This note turns the current DuckVEP objective into concrete phases:

- start from existing CSQ/ANN/BCSQ parsing in `read_bcf()`;
- port the smallest useful slice of `bcftools csq` consequence production;
- use DuckDB relations, Parquet, indexes, and interval primitives instead of inventing a new cache/archive format;
- keep Ensembl VEP and fastVEP as semantic references without inheriting their storage/runtime constraints;
- build a testing framework that can compare DuckHTS output to upstream VEP/bcftools on tiny fixtures first, then GIAB-scale data;
- keep TigerStyle/crash-safety cleanup in the path, especially top-level `src/` code.

Before claiming exact `bcftools csq` compatibility, establish and record an official bcftools tag/commit and validate against the executable for the declared scope.

## What already exists in DuckHTS

- `read_bcf()` already exposes typed INFO/FORMAT columns and typed `CSQ`/`ANN`/`BCSQ` subfields through `src/vep_parser.c` and `src/include/vep_parser.h`.
- `additional_csq_column_types` already mirrors bcftools-style type overrides for parsed annotation fields.
- `read_gff()` / `read_gtf()` expose GFF/GTF rows plus attribute map/list/pair forms.
- `fasta_nuc()` and FASTA readers provide reference sequence access.
- VariantKey and RegionKey functions provide exact-variant and compact-span keys.
- cgranges-backed functions provide interval overlap kernels.
- Parquet conversion helpers and DuckDB itself can persist annotation tables.

This means the first DuckVEP step should not be a new cache format. The first step should be schemas and SQL/native kernels over existing DuckDB-readable relations.

## DuckDB-native storage posture

Avoid custom fastSA/Sereal-style formats unless a measured bottleneck remains after ordinary DuckDB layouts.

Preferred local annotation assets:

1. **Transcript/feature pack** as DuckDB tables or Parquet:
   - `transcripts(transcript_id, gene_id, gene_name, biotype, chrom, start0, end0, strand, rank metadata...)`
   - `exons(transcript_id, exon_id, exon_number, chrom, start0, end0, strand, phase...)`
   - `cds(transcript_id, chrom, start0, end0, strand, phase, cds_rank...)`
   - optional `utr`, `regulatory`, `gene`, `protein`, `xref` tables
2. **Exact variant annotations**:
   - store `chrom`, `pos`, `ref`, `alt`, `variantkey`, reversible flag, payload columns;
   - join by `variantkey`, then refine non-reversible/hashing cases on original alleles.
3. **Region annotations**:
   - store `chrom`, `start0`, `end0`, optional `strand`, `regionkey`, payload columns;
   - use cgranges/interval kernels for actual overlap enumeration.
4. **Reference sequence**:
   - use FASTA via htslib initially;
   - add optional DuckDB-native sequence pack later only if profiling shows FASTA fetch dominates.

## Proposed engine/device architecture

Keep the consequence engine small and pluggable. Suggested internal devices:

- **Input device:** variant rows from `read_bcf()` or a relation with `chrom,pos,ref,alt`.
- **Exact-annotation device:** VariantKey-driven joins for dbSNP/ClinVar/cohort tables.
- **Region device:** transcript/exon/CDS/regulatory candidate generation through cgranges or SQL interval joins.
- **Consequence device:** allele/transcript-aware consequence classification.
- **HGVS device:** HGVSg first; HGVSc/HGVSp after transcript/CDS coordinate maps are validated.
- **Output device:** VEP-style tabular columns, CSQ strings, and/or BCSQ-compatible INFO/FORMAT fields.

The device boundary should be C structs/functions for hot paths and SQL macros/views for orchestration, not object-style C sprawl.

## Phased implementation plan

### Phase 0: cleanup and guardrails

- Treat `src/` as the authoritative C source tree. `r/Rduckhts/inst/duckhts_extension/` is generated by `r/Rduckhts/R/bootstrap.R`; do not hand-edit generated copies.
- Continue removing runtime `abort()` / `exit()` paths from top-level `src` where failures can be reported through DuckDB errors.
- Keep `goto cleanup` available for htslib-style ownership cleanup; TigerStyle concern is unstructured lifetime confusion, not gotos themselves.
- Add checked allocation helpers before broad allocation refactors.

### Phase 1: bcftools split-vep / parsed-annotation parity

Already mostly present:

- parse `CSQ`, `ANN`, `BCSQ` schema from VCF headers;
- expose typed list columns in `read_bcf()`;
- cover builtin and custom type rules in SQL/R tests.

Remaining work:

- add negative tests for malformed custom type rules;
- add a `BCSQ` fixture from bcftools output, not only VEP `CSQ`;
- document the exact subset: parsing existing annotations, not producing consequences.

### Phase 2: minimal bcftools csq producer

Target a deliberately narrow subset before haplotypes:

- normalized SNV/small-indel input;
- one GFF3 transcript model fixture;
- FASTA reference available;
- produce per-variant, per-transcript consequence rows;
- output a BCSQ-like string column for comparison.

Initial consequence terms:

- `intergenic_variant`
- `upstream_gene_variant` / `downstream_gene_variant`
- `intron_variant`
- `5_prime_UTR_variant` / `3_prime_UTR_variant`
- `splice_region_variant`
- basic coding SNV terms: `synonymous_variant`, `missense_variant`, `stop_gained`, `stop_lost`

Explicitly defer:

- haplotype-aware FORMAT/BCSQ bitmasks;
- multi-variant transcript haplotypes;
- SV/BND consequence logic;
- incomplete terminal codons;
- transcript consequence tie-breaking beyond a documented rank table.

### Phase 3: VEP-compatible output comparison

Use Ensembl VEP `release/115` as the semantic comparator for tiny fixtures:

- variant/transcript candidate selection;
- consequence terms and severity ranks;
- VEP tab/VCF CSQ field naming;
- HGVS fields once enabled.

Do not claim full Ensembl VEP parity until cache/database and plugin-dependent annotations are scoped.

### Phase 4: HGVS architecture

Implement in layers:

1. HGVSg for normalized small variants with reference accession/contig naming policy.
2. HGVSc using validated transcript coordinate maps.
3. HGVSp using codon translation and protein consequence state.
4. 3-prime shifting/normalization behavior as an explicit compatibility option.

VEP known-bug notes around multi-allelic HGVS and exon/intron boundaries should become regression cases, not hidden assumptions.

### Phase 5: GIAB and performance framework

Testing should scale in tiers:

1. tiny SQL fixtures committed under `test/data/duckvep/`;
2. script-generated fixtures recorded in manifests;
3. upstream comparison scripts for bcftools and VEP;
4. optional GIAB staging scripts that are not required for routine CI;
5. benchmark reports under `benchmarks/`, with DuckDB query plans and measured datasets.

GIAB validation should compare declared fields only: candidate counts, consequence-term distributions, selected exact rows, and performance. Do not use GIAB throughput as a proxy for semantic completeness.

## TigerStyle cleanup items specific to DuckVEP/csq

- New C should use small helpers and explicit `cleanup:` labels for ownership.
- No process aborts in runtime paths; use `duckdb_*_set_error` and return status codes.
- Use checked `size_t` arithmetic for all vector/table allocations.
- Keep parser state structs plain and small; avoid Java-style object graphs in C.
- Prefer SQL/DuckDB relations for orchestration and storage instead of custom binary caches.
- Add tests at the same time as each supported consequence term.

## First implementation slice recommendation

Start by adding a narrow, non-public internal SQL/C path that materializes transcript candidates from `read_gff()` and variant rows:

```sql
WITH variants AS (...),
     transcripts AS (...),
     candidates AS (
       SELECT v.*, t.transcript_id, t.gene_id, t.strand
       FROM variants v
       JOIN transcripts t
         ON v.chrom = t.chrom
        AND v.pos BETWEEN t.start1 - 5000 AND t.end1 + 5000
     )
SELECT * FROM candidates;
```

Then replace the naive range join with cgranges/interval kernels and add consequence labels one class at a time. This keeps semantics visible and avoids committing to a public API before upstream parity tests exist.
