# TigerStyle audit: DuckHTS + Rduckhts (2026-06-08)

## Scope
- **In scope:**
  - `src/*.c` (DuckHTS extension implementation)
  - `r/Rduckhts/R/*.R` (public R API)
  - `r/Rduckhts/inst/tinytest/*.R` (tests as executable examples)
- **Out of scope:**
  - bundled third-party code and build artifacts in `r/Rduckhts/inst/duckhts_extension/htslib/*`
  - third_party directories outside `src/`
- **Generation boundary:** the bundled R extension C tree under `r/Rduckhts/inst/duckhts_extension/` is generated by `r/Rduckhts/R/bootstrap.R` and should be treated as a copy artifact, not as a primary editing target.
- **Method:** lightweight static checks for commonly observed TigerStyle patterns (line length, function size, control-flow readability, assertions, and error-handling ergonomics).

## Executive findings
The codebase is largely functional and performance-oriented but **not TigerStyle-compliant by default**.

- **Function-size discipline:** many long functions remain in performance-critical C paths.
- **Line width:** several long lines in both C and R (especially generated/legacy SQL glue).
- **Control-flow explicitness:** extensive use of compact one-line conditionals in C.
- **Error-as-values posture:** runtime failures are mostly reported through DuckDB/R error paths (`duckdb_*_set_error`, `duckdb_function_set_error`, `duckdb_scalar_function_set_error`, `stop()`), which aligns with non-crashing runtime behavior.
- **Style enforcement in CI:** no dedicated TigerStyle gate is visible in current scripts.

## Quantified deviations

### 1) Function length
TigerStyle prefers short, single-purpose functions.

- **C (`src/*.c`): 65 functions > 70 lines**
- **R (`r/Rduckhts/R/*.R`): 2 functions > 70 lines** (`bootstrap.R`)
- **R tests (`inst/tinytest/*.R`): 16 functions > 70 lines** (many large monolithic test scripts)

Top offenders (C):
- `cgranges_api.c` — 8
- `hts_meta_reader.c` — 8
- `bam_bin_counts.c` — 6
- `tabix_reader.c` — 6
- `score_udf.c` — 5
- `interval_udf.c` — 4
- `bam_bed_coverage.c`, `bam_reader.c`, `bcf_reader.c`, `liftover_udf.c`, `mosdepth_table.c`, `seq_reader.c` — 3 each
- others: `bam_pileup.c`, `kmer_udf.c`, `samtools_idxstats_table.c`, `bgzip.c`, `hts_index_builder.c`, `munge_udf.c`, `variantkey_udf.c`

**Potential remedy:** split largest kernel-style functions (notably in `bcf_reader.c`, `bam_bed_coverage.c`, `liftover_udf.c`, `score_udf.c`, `mosdepth_table.c`) into smaller stage functions (input validation, allocation, scan loop, emit phase). Add `TODO`-style split markers before large rewrites.

### 2) Long lines
TigerStyle strongly prefers compact lines.

- **C (`src/*.c`): 851 lines > 100 chars** (excluding vendored `bcftools_filter.c`), **1088** if included.
- **R (`r/Rduckhts/R/*.R`): 28 lines > 100 chars**.
- **R tests:** 96 lines > 100 chars.

Worst-affected files (C):
- `score_udf.c`, `liftover_udf.c`, `cgranges_api.c`, `samtools_idxstats_table.c`, `variantkey_udf.c`, `duckhts.c`
- `bam_bed_coverage.c` also contributes many long formatted call lines.

**Potential remedy:** wrap nested ternaries/format strings, break argument lists, and extract long SQL or error-string construction into local variables/constants.

### 3) One-line/compact conditionals
TigerStyle favors explicit braces and clearer branching blocks.

- **~1,940** one-line `if (...) ...;` occurrences in first-party `src/*.c` (excluding `bcftools_filter.c`).
- `if (cond) return ...;` and `if (cond) continue;` patterns are especially frequent in read loops.

**Potential remedy:** enforce braces for all control statements in new/edited files; prefer early-return helpers with named predicates to reduce branch nesting.

### 4) Assertions and invariants
Given this constraint (no host/crash), favor **error-return APIs** over assertions for runtime behavior.

- **C (`src/*.c`, excluding `bcftools_filter.c`): 0 `assert(...)` calls found**.
- **R:** no consistent `assertthat`-style invariant API in reviewed files.
- Most failures are already expressed via DuckDB/htslib return codes and explicit `*_set_error` calls.

**Potential remedy (non-crashing):**
- Keep using `duckdb_*_set_error`, `duckdb_init_set_error`, `duckdb_function_set_error`, and `duckdb_scalar_function_set_error` for recoverable/expected failures.
- Use `assert`/abort only for truly unrecoverable, debug-only programmer invariants when absolutely necessary, and avoid exposing them in production paths.
- In R, keep explicit argument contract checks (type, length, nullability) near API entry points.

### 5) Explicit cleanup and resource ownership
Large performance paths rely heavily on manual allocation with many `malloc`/`free` sites.

- Repeated manual ownership patterns were observed across most readers/normalizers.
- A few paths contain long allocation/finalization blocks, which makes leak/error-path drift likely during edits.

**Potential remedy:** define/centralize local cleanup sections (`cleanup:` goto labels or helper destructors), and document ownership on all heap objects in function-local comments/headers. `goto cleanup` is acceptable and often preferred here when it follows htslib-style single-exit ownership discipline; avoid only unstructured gotos that obscure lifetime or error semantics.

### 6) Type clarity and narrow contracts
Given heavy genomics parsing, implicit conversions are frequent in fast paths.

- Code contains many casts between DuckDB types, index counters, and parser offsets.
- This is typical for low-level code, but TigerStyle prefers bounded, explicit conversion points.

**Potential remedy:** isolate conversion boundaries in named helpers (`to_idx_t`, `checked_to_int32`, etc.) and add comments for explicit truncation/rounding assumptions.

### 7) Test and style readability debt (R tinytest)
Several tinytest files are huge monoliths with many long functions and long lines.

- `test_bcftools_norm.R` (~457 lines in one function)
- `test_liftover.R` (~706)
- `test_mosdepth.R` (~603)
- `test_munge.R` (~324)
- `test_type_mappings.R` (~438)

**Potential remedy:** break out reusable helpers and subtests; retain one large scenario only where necessary.

### 8) CI linting / guardrails gap
No explicit TigerStyle-compatible style check is currently documented in build/CI commands.

**Potential remedy:** add a repository-specific style target, e.g. `make style-check`, that enforces:
- function length budget (with vendored exclusions)
- line length budget
- brace style for conditionals
- optional assertion density checks for new code paths

## Remediation approach (low-risk ordering)
1. **Scope and baseline** (today): create exclusion list for vendored/legacy files and freeze baseline counts.
2. **Gate new contributions**: require TigerStyle on changed hunks only (do not bulk-reformat all legacy paths at once).
3. **Refactor highest-risk kernels**: start with `src/score_udf.c`, `src/mosdepth_table.c`, `src/liftover_udf.c`, `src/duckhts.c`.
4. **R API parity pass**: enforce small helper-driven `duckhts.R`/`bootstrap.R` functions.
5. **Tinytest modularization**: split very large tests into grouped helpers while preserving coverage.

## Notes
- Some deviations are inherited from legacy/ported upstream code and performance-oriented idioms. Full remediation should be done iteratively to avoid regressions in hot-path behavior.
- This audit is structural/style-only; it does **not** assess runtime correctness or biological semantics.
